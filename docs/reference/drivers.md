# 用户态驱动

驱动是普通的用户进程。init 启动它之前把它的设备许可给它，之后它只碰得到这一个设备（机制见 [特权与硬件访问](hardware.md)）。现在有五个：串口 `user/uart`、PS/2 键盘 `user/kbd` 和 USB 键盘 `user/usbkbd`（这两个只有 PC 有）、磁盘 `user/blk`（virtio-blk，PC 上还有 IDE 硬盘和 U 盘），以及和协议栈在同一个进程里的网卡驱动（`user/net/nic.cpp`，见 [网络](net.md)）。前三个是输入设备，收到的字符都交给终端输入服务 `user/console`；virtio 设备的公共部分在 `user/lib` 的 `virtio.h`。

## 终端输入：console

`user/console` 是终端输入服务，不是驱动，不碰硬件：输入设备的驱动把收到的字符用 `CONSOLE_INPUT` 送到这里（用户库的 `console_input`），它再分给读者。从这里起字符不分来源，命令行和程序不知道输入来自串口还是键盘。

1. 主循环 `ipc_recv(IPC_ANY)`：收到 `CONSOLE_INPUT` 就把字符放进缓冲区；收到 `CONSOLE_READ` 请求就记下读者。
2. 缓冲区里有数据且有读者在等时，把数据作为应答发回去。读者有两个（终端的主人和前台进程），各有各的缓冲区，新到的字节按当时有没有前台进程分到其中一个。读请求可以带超时：到时间还没有输入就应答 0 字节（它用 `timer_set` 给自己定时）。

只有登记了 `"uart"`、`"kbd"` 或 `"usbkbd"` 的进程发来的 `CONSOLE_INPUT` 才被接受；这几个名字是 init 留给那几个驱动的，别的进程登记不了。

协议定义在 `user/lib/include/console.h`，同一个头文件里是读键盘输入的客户端函数 `console_read` / `console_read_line`；程序一般不直接用它们，而是用 `stdio.h` 的 `read_line` / `read_input`（标准输入可能被重定向）。它以 `"console"` 这个名字登记。

`CONSOLE_DEBUG_EXIT` 是调试用的请求：`console` 和输入设备的驱动收到它都在应答之后立刻退出，像崩溃了一样，用来验证 init 会重启它们、输入随后照常（`selftest restart <名字>` 发这个请求，`make test` 的命令行检查用它）。

## 串口：uart

`user/uart` 是串口输入驱动：x86 的 16550 通过 I/O 端口访问，arm64 的 PL011 用 `map_device` 把寄存器映射进来直接读写。内核只用串口做输出，接收方向完全在驱动里：

1. 启动时从许可表里取出自己的设备（`hw_find`：端口或设备内存，以及中断线），`irq_claim` 串口中断，打开设备的接收中断。
2. 每次中断把硬件 FIFO 里的字节读完，交给 `console`，然后 `irq_ack`。

它以 `"uart"` 登记，登记只是为了让 `console` 认得它；除了 `CONSOLE_DEBUG_EXIT` 它不接受任何请求。没有串口的机器上（x86 上启动时往串口的暂存寄存器写一个值再读回来，读到的不一样就是没有）它直接退出，输入就全部来自键盘。

## PS/2 键盘：kbd

`user/kbd` 是 PS/2 键盘驱动，只在 x86 上构建。PC 的键盘（包括笔记本的内置键盘）接在键盘控制器上：数据端口 `0x60`，状态和命令端口 `0x64`，1 号中断；init 把这三样许可给它。

1. 启动时把控制器设成需要的状态，不管固件留下的是什么：键盘接口打开并产生中断，扫描码翻译成第 1 套，鼠标接口关掉（没有人读它，它的字节会堵住键盘的）。
2. 每次中断把控制器里的扫描码读完。一个键按下和松开各有一个扫描码；驱动记着 Shift、Ctrl 和 Caps Lock 的状态，把按下的键翻译成字符（Ctrl 加字母是对应的控制字符，Ctrl-C 就是 `0x03`；修饰键怎么作用在一个键上是和 `usbkbd` 共用的，`user/lib` 的 `keys.h`）。方向键、Home、End 和 Delete 不产生字符，驱动把它们送成终端上通用的转义序列（上是 `ESC [ A`，按着 Ctrl 的左右方向键是 `ESC [ 1 ; 5 D` / `C`，同在 `keys.h`），和串口那头的终端送来的一样，由读输入的一方去认（见 [行编辑和历史](shell.md#行编辑和历史)）。
3. 翻译出的字符用 `CONSOLE_INPUT` 交给 `console`。终端的主人、前台进程这些概念它一概不知道。

它以 `"kbd"` 登记，和 `uart` 一样除了 `CONSOLE_DEBUG_EXIT` 不接受任何请求。

当前的限制：美式键盘布局；功能键、Insert、Page Up / Page Down、小键盘的数字和 Alt 没有对应的字符，按了没有反应。

## USB 键盘：usbkbd

`user/usbkbd` 是 USB 键盘驱动，只在 x86 上构建。USB 键盘是低速或全速设备，归 USB 1.1 的控制器管；这里认的是 UHCI（Intel 和 VIA 芯片组上的那种）。一台机器上常有好几个，init 把它们都许可给这一个进程（最多 4 个）。它分两层，各在自己的源文件里：

- **找到并接管控制器（init）**：在 PCI 配置空间里按类别找（`pci.h`），打开它的端口访问和总线主控。固件可能正用着它，把 USB 键盘装成 PS/2 键盘给没有驱动的系统用——靠的是控制器一有事就打断系统、转去执行固件；init 在配置空间的交接寄存器里把这些关掉，让控制器停下，再把它的寄存器（32 个端口）和中断线许可给 `usbkbd`。从这时起键盘不再经过固件，敲的键只从 USB 这条路来。
- **控制器驱动（`uhci.cpp`）**：UHCI 把时间切成 1 毫秒一帧，有一张 1024 项的帧表，每一帧从表里的一项出发沿着指针走一遍，走到的传输各做一次。要做的传输是内存里的“传输描述符”（一个包一个：方向、设备地址、端点、缓冲区的物理地址），挂在“队列头”下面；这些都来自 `dma_alloc`。驱动准备了 8 个队列头用来定期问设备有没有数据（每个键盘占一个），另有一个控制传输用的队列头；帧表里每 8 项有一项经过前者，所以键盘每 8 毫秒被问一次。
- **认设备（`usbkbd.cpp`）**：USB 设备可以随时插拔，而 UHCI 不为此发中断，所以每 250 毫秒看一眼每个口。新插上的设备（连着两次都看到它在，免得把触点的抖动当成设备）复位、给地址、读设备描述符和配置描述符。是集线器就按下面说的接着管它的口；否则在配置描述符里找“人机接口设备、会启动协议、键盘”的接口和它的中断输入端点；两样都不是就关掉那个口不再理它，直到它被拔掉。
- **集线器**：集线器是“更多的口”。它自己是一个设备，口上的事要发请求问它：给口上电、口上有没有设备、有没有插拔过、复位（复位信号保持多久、之后打开这个口，都是集线器自己做）。驱动把“看一眼、复位、关掉”这三件事对两种口各写一份，再往上就不分是控制器自己的口还是集线器上的口，所以集线器后面还可以接集线器，拔掉一个集线器时它后面的设备一起放手。低速的键盘接在全速的集线器后面，控制器发包时替它打招呼，驱动只要记着它是低速的。
- **读键盘**：让键盘用“启动协议”——所有键盘都会的一种固定格式，每份报告 8 个字节：一个字节的修饰键，最多 6 个此刻按着的键的编号。键盘在按键有变化时给一份报告，控制器收到时发中断。驱动把它和上一份比，多出来的就是刚按下的键，翻译成字符用 `CONSOLE_INPUT` 交给 `console`。按住不放的键由驱动自己重复（半秒之后每 40 毫秒一次）：PS/2 键盘自己会重复，USB 键盘只报告“按着”。

和 USB 2.0 控制器的关系：机器的每个 USB 口背后有两个控制器，高速设备归 EHCI，其余的归它的“伙伴”UHCI，由 EHCI 上的一个开关决定每个口现在接到谁那里。`blk` 的 EHCI 驱动启动时把所有口都要过去，逐个复位；发现上面不是高速设备，就把那个口让回给伙伴控制器，`usbkbd` 随后在自己的端口上看到“插上了一个设备”。所以它不能只在启动时找一次键盘。高速的集线器（USB 2.0 的集线器都是）也让过去：到了伙伴控制器那边它按全速工作，后面的键盘就能用了；代价是它后面的 U 盘也跟着过去，而那边没有人认 U 盘。

它以 `"usbkbd"` 登记，除了 `CONSOLE_DEBUG_EXIT` 不接受任何请求。机器上没有 UHCI 控制器时它直接退出。`make run KBD=usb` / `make test KBD=usb` 给虚拟机接一个 USB 键盘，`KBD=hub` 把它接在一个集线器后面。

当前的限制：只认 UHCI，USB 1.1 的另一种控制器 OHCI（AMD、NVIDIA、SiS 芯片组）没有驱动；键盘和集线器加起来最多 16 个，每个控制器上最多 8 个键盘，一个集线器只管它的前 8 个口；集线器的口每 250 毫秒各问一次，没有用它报告“有变化”的那个端点；只用启动协议，一次最多 6 个键，多媒体键没有反应；键的翻译和 `kbd` 一样（美式布局，功能键、Insert、Page Up / Page Down、小键盘的数字和 Alt 没有字符）；Caps Lock 的状态所有键盘共用一个，灯只在按下它的那个键盘上跟着变；机器有 EHCI 时，启动之后才插上的键盘要等 `blk` 把口让出来，而它只在启动时做一次，所以键盘（和它前面的集线器）要在开机前插好；只在 QEMU 里验证过，而 QEMU 的键盘和集线器都是全速设备：低速设备的那条路、把高速集线器让给伙伴控制器的那一步、真机上从固件手里接管控制器的那一步都没有跑过。

## virtio 的公共部分

virtio 设备的公共部分（legacy 接口：找设备、寄存器访问、队列）在 `user/lib` 的 `virtio.h` 里，块设备和网卡驱动共用。两种接入方式只是寄存器的访问方法不同：

- **x86**：virtio-pci。寄存器在设备的 I/O 端口 BAR 里。
- **arm64**：virtio-mmio。寄存器用 `map_device` 映射进来。

找设备和用设备是两个进程的事，各有一个函数。`virtio_allow(类型)` 由 init 在即将成为驱动的子进程里调用（这时还有特权）：x86 上通过 0xCF8/0xCFC 端口扫描 PCI 配置空间，（只看 0 号总线上的 32 个设备位置）量出 BAR 占多少个端口，读出中断线，打开设备的端口访问和总线主控；arm64 上向内核查设备树里的 32 个 virtio-mmio 槽位，逐个映射进来看里面是什么设备。找到之后把寄存器和中断线记进许可表。`virtio_open` 由驱动调用：许可表里的端口（或设备内存）和中断线就是它的设备。驱动自己不扫总线，也碰不到 PCI 配置空间。

`virtio_allow` 找到设备之后还会把它复位。平时这是多余的；驱动崩溃后被 init 重启时不是：上一个驱动留给设备的队列还指着它（已经被收回的）内存，要在新驱动启动之前让设备停下来。

队列和请求缓冲区来自 `dma_alloc`（设备只认物理地址）。

当前的限制：只支持 legacy 接口（QEMU 的默认配置）。

## 块设备：blk

`user/blk` 是块设备驱动，以 `"blk"` 登记。块设备的协议和客户端接口在 `user/lib`（`blk.h`）：`blk_capacity`、`blk_read`、`blk_write`，以 512 字节扇区为单位，数据同样经客户与驱动之间的共享缓冲区传递。

块设备驱动一次处理一个请求：提交给设备后用 `ipc_recv(IPC_FROM_KERNEL)` 只等中断，这期间其他客户的请求留在各自的 `call` 里排队。

关机或重启之前 init 给它发 `BLK_STOP`（见 [微内核结构](../microkernel.md) 的“关机和重启”）：它让每块盘把自己缓存里还没写到介质上的内容写下去（`disk.h` 里的 `flush`），应答，然后退出。IDE 硬盘每次写完已经落盘了；virtio-blk 没有向设备要“写缓存”这个特性，设备那边就得每次写完都落盘；所以真正有事可做的只有 U 盘。

它可以同时管着几块盘（PC 上的硬盘和 U 盘），从 0 编号，请求里带着编号；客户端库的 `blk_count` 问有几块，`blk_select` 选之后的读写用哪一块（一开始是 0 号）。

它认三种设备，各在自己的源文件里，公共的部分（`blk.cpp`：收请求、检查范围、把中断分给设备）通过 `disk.h` 里的几个函数用它们：

- **virtio-blk**（`virtio_blk.cpp`）：QEMU 里默认用的。
- **IDE 硬盘**（`ata.cpp`，只有 x86）：老 PC 的硬盘。init 找不到 virtio 磁盘时，把第一个 IDE 通道许可给它：任务文件的 8 个端口 `0x1F0`–`0x1F7`、控制端口 `0x3F6` 和 14 号中断，这些在 PC 上是固定的。驱动复位通道，用 `IDENTIFY` 命令问主盘的型号和容量，没有盘就退出。读写用 PIO 方式：每个扇区的 512 字节通过数据端口一个字一个字地搬。设备每忙完一步发一次中断；驱动另外每 10 毫秒自己看一眼状态，中断丢了也不会一直等下去。每个写请求之后发一次 `FLUSH CACHE`，应答“写好了”时数据已经在盘上。
- **U 盘**（`usb_storage.cpp` 和 `ehci.cpp`，只有 x86）：见下面一节。init 在许可 IDE 通道的同时，在 PCI 上找 USB 2.0 的控制器，找到就一并许可给它。

有哪些设备看许可表的样子（IDE 通道是 8 个端口加 1 个端口，USB 控制器是一段设备内存），不靠试：把一种设备的寄存器当成另一种的去写会让设备做出谁也不想要的事。`DISK_BUS=ide` 和 `DISK_BUS=usb`（`make run` 和 `make test` 都认）把 QEMU 的磁盘接成 IDE 硬盘、或者插在 USB 2.0 口上的 U 盘。

### USB 2.0 和 U 盘

USB 上设备从不主动说话，每个包都是主机发起的，主机这边由控制器代劳。USB 2.0 的控制器是 EHCI：驱动把要做的传输写成内存里的数据结构，控制器照着去收发，做完把结果写回同一块内存。

- **找到并接管控制器（init）**：在 PCI 配置空间里按类别找到它（`pci.h`），打开它的设备内存访问和总线主控。固件可能正用着它（让 USB 键盘、U 盘在没有驱动时也能用，从 U 盘启动时尤其如此），所以要在配置空间里的交接寄存器上把控制权要过来，并关掉固件留下的中断。然后把它的寄存器（一段设备内存）和中断线许可给 `blk`。
- **控制器驱动（`ehci.cpp`）**：复位控制器，建一个“队列头”的环——每个队列头代表一个设备的一个端点，控制器一圈一圈地走。要传数据时填一串“传输描述符”（方向、长度、缓冲区的物理地址）挂到端点的队列头上，等控制器清掉最后一个描述符的 Active 位。这些结构和数据缓冲区都来自 `dma_alloc`。控制器做完时发中断；另外每 10 毫秒自己看一眼，中断没来也不会一直等。
- **认设备（`usb_storage.cpp`）**：逐个复位端口。上面是高速设备的话，给它一个地址，读它的配置描述符，在里面找“大容量存储、SCSI 命令、仅批量传输”的接口和它的两个批量端点，选中这个配置。
- **读写**：U 盘听的是磁盘的那套 SCSI 命令，装在 USB 的信封里：往批量输出端点发一个 31 字节的命令包，在批量端点上传数据，再从批量输入端点收一个 13 字节的状态包。启动时等它准备好（`TEST UNIT READY`），问型号和容量，之后就是 `READ(10)` 和 `WRITE(10)`。设备用“挂起端点”表示某一步不行，驱动解除挂起后照样收状态包；三步走乱了就让设备复位到“等新命令”的状态。

当前的限制：只认直接插在机器 USB 2.0 口上的第一个高速 U 盘，不认集线器后面的 U 盘（集线器整个让给了伙伴控制器，见 [usbkbd](#usb-键盘usbkbd)）；只在启动时找一次，之后插拔不知道；低速和全速设备（键盘、鼠标、USB 1.1 的 U 盘）归另一种控制器管，这里把端口让出去就不管了（键盘由 [usbkbd](#usb-键盘usbkbd) 接手）；只支持 512 字节扇区、2TB 以内；只在关机和重启之前要求设备把自己的缓存落盘（`SYNCHRONIZE CACHE`），平时每次写完不要求，写了马上拔掉或者断电可能丢；只在 QEMU 里验证过，真机上从固件手里接管控制器的那一步没有跑过。

`make run` 给 QEMU 挂上 `disk-<arch>.img`（根文件系统，16MB，`make clean` 不删，每个架构一个）；`make test` 每次用一块新做的 4MB 磁盘，小到自检可以把它写满来检查“磁盘满”的处理（大于 4MB 的磁盘上这一项会跳过）。`make test` 的环境里磁盘、网卡、回显服务都在，所以自检里出现任何 skipped 也算失败（`LIVE=1` 不接磁盘时，和磁盘有关的那几项除外）。

当前的限制：一次一个请求，没有并发；每个请求最多 8 个扇区。IDE：只认第一个通道上的主盘；没有 DMA，数据靠 CPU 一个字一个字地搬；扇区号 28 位，大于 128GB 的盘只用前 128GB。分区是文件系统的事，驱动把整块盘当成一个设备。
