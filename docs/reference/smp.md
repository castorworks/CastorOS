# 多个 CPU

CastorOS 可以用机器上所有的 CPU 同时运行用户进程，三个架构都支持。

```bash
make run ARCH=arm64 SMP=4       # 给虚拟机 4 个 CPU
make test ARCH=x86_64 SMP=4     # 带着 4 个 CPU 跑全部测试
```

不写 `SMP` 就是一个 CPU。内核最多用 8 个（`MAX_CPUS`；arm64 的 QEMU virt 用的 GICv2 本来也只支持 8 个）。

## 办法：一把内核锁

内核原本的假设是只有一个 CPU：关了中断就没有别人（见 [同步](../concepts/06-synchronization.md)）。有了几个 CPU，这个假设靠一把锁留住：

> 任何 CPU 执行内核代码之前都要拿到内核锁，所以同一时刻只有一个 CPU 在内核里。

拿着这把锁的内核代码因此一行都不用改，原来“关中断”保护的东西照样安全。用户态的代码不归这把锁管：几个 CPU 可以同时运行几个用户进程，这就是多 CPU 带来的全部好处。微内核在这一点上占便宜——文件系统、网络、驱动都是用户进程，它们真的在并行；内核自己每次进来只做很短的事，排一下队代价不大。

代价也很清楚：**拿着这把锁的内核代码不并行**。两个进程同时做系统调用，要一个等另一个——除非那个调用已经从这把锁底下挪了出来（见下面“不拿内核锁的系统调用”）。

锁在 `src/kernel/smp.cpp`（`kernel::KernelLock`）。拿锁和放锁都写在 C++ 里，位置是各架构进内核之后最先到的那几个函数：系统调用的 `syscall_dispatcher`，x86 的 `irq_handler` / `isr_handler`（和它们的 64 位版本），arm64 的 `arm64_exception_handler`。什么时候拿、什么时候放：

| 时候 | 做什么 |
|------|--------|
| 从用户态进内核（系统调用、中断、异常） | `enter()`：拿锁，拿不到就空转着等 |
| 回用户态之前 | `release()`：放锁 |
| 中断打断的是内核自己（这个 CPU 已经拿着锁） | `enter()` 只把嵌套计数加一，回去时 `leave()` 减一 |
| 任务被换下 CPU | 记下它拿着几层（`task_t::lock_depth`），这个 CPU 的锁交给换上来的任务处置 |
| 任务被换上 CPU | 恢复成它被换下去时的层数（`adopt()`）：原来拿着就再去拿，原来没拿就放掉 |
| idle 任务 | 从不拿：它只碰调度器，调度器有自己的锁。它等中断时来了中断，处理函数自己 `enter()`、自己 `leave()` |

**锁跟着任务走。** 一个任务在内核里睡下去时（等子进程、睡眠、`mem_grant` 等对方收通知）可能拿着内核锁，也可能没拿（IPC 的调用不拿）；换上来的任务同样两种都有。所以切换任务时锁要跟着换：`schedule()` 把换下去的任务拿着几层记在它的 PCB 里，换上来的任务一站到自己的栈上（`finish_switch`），就把这个 CPU 拿锁的层数改成它自己当初的那个数——两边一样就什么都不用做，锁原样留在这个 CPU 手里；换上来的没拿就放掉；换上来的拿着而这个 CPU 现在没拿，就去等。对每个任务来说，这和“我一直拿着锁，只是中间睡了一觉”没有区别；对别的 CPU 来说，拿着内核锁睡觉的任务不挡路。

一个新进程第一次运行时没有“从系统调用或中断返回”的那条路可走。所以它不是从任务切换直接跳进用户态的：它的现场被安排成先在内核态、自己的内核栈上运行一小段（`sched.cpp` 的 `user_task_start`），在那里做和别的任务换上来时一样的收尾（新任务的层数是 0，所以是放锁），再装上真正的用户态现场。

`release()` 是“不管嵌套了几层都放掉”，而不是减一：有的路径进来了就不再按原路回去（进程在异常处理里退出，换上来的是另一个任务），而回用户态时这个 CPU 一定不该再拿着锁。

## 不拿内核锁的系统调用

一把大锁是起点，不是终点：把它拆开的办法，是一个调用一个调用地证明“它不需要这把锁”，然后让它不拿。`src/kernel/syscall.cpp` 里有一张表 `syscall_unlocked`，列在里面的系统调用进内核时不拿内核锁，几个 CPU 上的进程可以同时在里面。现在有这些：

| 调用 | 为什么可以 |
|------|------------|
| `mmap`、`munmap`、`brk` | 改的是调用者自己的地址空间和堆边界；物理页帧（PMM）和页表（VMM）各有自己的锁 |
| `ipc_send`、`ipc_recv`、`ipc_call`、`ipc_reply` | 消息、谁在等谁、叫醒对方，都在调度锁里（见下面“调度器和 IPC”） |
| `getpid`、`hw_allowed` | 只读调用者自己的东西 |
| `cpu_info`、`mem_free_pages` | 读一个数，读的地方自己带锁，或者读到旧值也无妨 |

**规矩。** 一个调用要列进这张表，它的整条路径只能碰三类东西：

1. 调用者自己的、别人不会同时读写的东西（它的寄存器帧、堆边界、许可表）；
2. 自己带锁的子系统：物理页帧、页表、内核堆、控制台输出、调度器（阻塞、唤醒、切换任务）；
3. 只读的、或者读到旧值也无妨的全局量。

还要想清楚“别的进程碰得到调用者的哪些地方”，因为那些进程可能拿着内核锁在碰，和这边互不相让。拿着自旋锁的时候不能碰用户内存：那可能缺页，缺页处理要拿内核锁，而别的 CPU 可能正拿着内核锁等这把自旋锁。

**为了内存的调用，改了三处：**

- **共享内存和 mmap 分开用地址。** 往一个地址空间里放映射的只有两种人：进程自己，和用 `mem_grant` 把内存共享给它的别的进程。两边要是在同一段地址里找空闲位置，就可能挑中同一段。给地址空间加一把锁是一种办法；这里用的办法更简单：堆和栈之间那段地址分成两块，进程自己的 `mmap`（和设备内存、DMA 内存）用前一块，别人共享进来的用后一块（`GRANT_REGION_START`，`src/kernel/syscalls/mm.cpp`）。各在各的那块里找，不用商量。这条路上对页表的修改（建映射、撤映射）原本就都在 VMM 的锁里做。
- **清零挪到 PMM 的锁外面。** 分配一个页帧要清零，清一页比在位图里记一笔慢得多。页帧记到名下之后就没有别人会碰它，所以先放锁再清。几个 CPU 同时要内存时，它们只在记账上排队。
- **控制台有了自己的锁。** 原来“一条日志不被另一条插进来”靠的是关中断加内核锁。不拿内核锁的代码也会打日志，所以输出入口改成拿控制台自己的锁（`ConsoleGuard`，同一个 CPU 可以嵌套）。

**调用结束时。** 别的进程发来的 `kill` 是在系统调用返回前生效的，而退出要动任务表和调度器，得拿着内核锁。不拿锁的调用结束时先看一眼自己身上有没有待处理的请求（只有自己会清它），有才去拿锁。

**中断照旧。** 不拿锁的调用执行到一半来了中断，处理函数自己拿锁、自己放，和中断打断 idle 的等待时一样；它不会切换任务（只在回用户态的出口切换）。

自检里有一项专门压这条路：每个 CPU 一个进程，同时反复 `mmap`、写满、长堆缩堆、`munmap`，中间夹着 `fork`（写时复制）和把页共享给父进程；每个进程看到的内容都必须是自己写的，全部结束后空闲页数一页不少。

## 调度器和 IPC

微内核里最频繁的系统调用是 IPC：读一个文件是几次 `call`，每次 `call` 是客户和服务各进两次内核。它们要是都排在内核锁后面，几个 CPU 上的服务就并行不起来。但 IPC 和调度器缠在一起——收发消息会睡下去、会叫醒对方——所以先得让调度器不靠内核锁。

### 调度锁

调度器有自己的一把自旋锁（`task_lock`，拿的时候关中断）。它保护就绪队列，和每个任务的这些东西：状态（`state`）、在等什么（`wait_object`、`sleep_until_ms`）、是不是还在某个 CPU 上（`on_cpu`）、IPC 的那几个字段、待处理的内核消息（设备中断、定时器）。改任务的状态一律在这把锁里。

**睡下去不会错过叫醒。** 等一件事的代码都是同一个样子：拿锁，看条件，不满足就把自己标成 `BLOCKED`，放锁，`schedule()`。让条件成立的一方也在锁里：改条件，把对方标成 `READY`。两边不会交错——要么等的一方先拿到锁，那叫的一方看到的是 `BLOCKED`，会叫；要么叫的一方先，那等的一方看到条件已经成立，根本不睡。

**还在 CPU 上的任务不进就绪队列。** 上面那段里有一个缝：等的一方放了锁、还没切换走的时候，别的 CPU 已经把它叫醒了。如果这时就把它放进就绪队列，第三个 CPU 可能把它取走，在它还没让出来的内核栈上运行。所以每个任务有一个标记 `on_cpu`，被换上 CPU 时置位；叫醒一个 `on_cpu` 的任务只改状态，不进队列。换它下去的那个 CPU 切换完成之后（已经站在下一个任务的栈上，`finish_switch`）清掉标记，这时如果它的状态是 `READY`——时间片用完被换下的，或者途中被叫醒了的——才把它放进队列。从队列里取出来的任务，栈一定没人在用。

退出的任务同理：它不能在自己的栈上释放自己，所以也是 `finish_switch` 把它挂到待清理的链表上，之后进 `schedule()` 的 CPU 来释放。

### IPC

`src/kernel/ipc.cpp` 的每个操作从头到尾拿着调度锁：找到对方、看它是不是正等着这条消息、把消息拷进它的 PCB、把它叫醒，是一个不可分的动作。要等的时候在锁里标好自己的状态（在发、在收、等谁），放锁去切换；被叫醒后重新拿锁，取结果。设备中断和定时器到期也走同一把锁：记下“有内核消息待处理”，目标正在 `recv` 上等的话直接交给它（`UserIrq::raise`、`Scheduler::timer_tick`）。

三处要留意的地方：

- **消息先拷到内核栈上。** 锁里搬的是内核里的副本，系统调用的入口负责和用户内存之间的拷贝（`syscall.cpp` 的四个包装函数）。锁里碰用户内存可能缺页，见上面的规矩。
- **正在退出的进程。** 进程退出时先把等它的进程都叫醒（它们得到 -1），到它真的变成僵尸还有一小段。这期间别的 CPU 上的进程不能再开始等它，否则没人来叫了。所以退出的第一步是在锁里把自己标成“不再通信”（`IPC_CLOSED`），发给它的消息从这一刻起立刻失败。
- **`kill`。** 终止请求在调度锁里记到目标身上，并把正等着 IPC 的目标叫醒；等待的循环每次睡下去之前在锁里看一眼有没有这个请求。所以不会出现“请求记上了，目标却刚好睡下去”。

`mem_grant` 还拿着内核锁，它的最后一步是给对方发授予通知，可能要等对方来收——这时它是一个拿着内核锁睡觉的任务，锁在它被换下去时交了出去。

自检里有一项专门压这条路：每个 CPU 一个客户进程，同时向一个服务 `call`，各自还带一个伙伴进程 `send`/`recv` 来回传，中间夹着等定时器；每个回答都必须是对的、是给自己的。任何一次漏掉的叫醒都会让它做不完。

## 每个 CPU 自己的东西

每个 CPU 有一个编号，`hal::Cpu::id()`，0 是启动时的那个。arm64 上它放在 `TPIDR_EL1` 寄存器里。x86 上每个 CPU 把自己的 TSS 描述符放在 GDT 里不同的位置，于是每个 CPU 的任务寄存器里的选择子都不一样，读一下（`str` 指令）就知道自己是几号。下面这些每个 CPU 各有一份，按编号放在数组里：

| 什么 | 在哪里 |
|------|--------|
| 正在运行的任务、idle 任务、时间片计数、“该换人了”的标记、正在换下去的那个任务 | `src/kernel/sched.cpp` 的 `per_cpu[]` |
| 中断嵌套了几层 | `src/kernel/interrupt.cpp` |
| 现在用的是哪张页表 | `src/mm/vmm.cpp` |
| 内核锁拿了几层 | `src/kernel/smp.cpp` |
| x86：GDT 和 TSS（进内核时用的内核栈、I/O 许可位图） | `src/arch/<arch>/cpu/gdt*.cpp` |
| x86_64：`syscall` 指令入口用的内核栈 | `src/arch/x86_64/syscall/syscall64.cpp`，入口代码用 `swapgs` 找到自己的那一份 |

就绪队列只有一个，所有 CPU 共用，由调度锁保护：哪个 CPU 进了调度器，就从队首取下一个任务。所以一个进程这次在 CPU 0 上运行，下次可能在 CPU 2 上——它的寄存器、浮点状态、页表都跟着 PCB 走，哪个 CPU 都能接着运行它。每个 CPU 有自己的时钟中断，各自给自己正在运行的任务计时间片。

设备中断只送到 CPU 0。任务表最前面的 8 个 PCB 留给各个 CPU 的 idle 任务。

最后一行值得多说一句。x86_64 的 `syscall` 指令不换栈，入口代码的头几条指令要自己找到内核栈，而这时还没有拿内核锁——两个 CPU 可以同时执行到这里。所以“内核栈在哪”不能是一个全局变量，必须每个 CPU 一份；入口代码靠 GS 段的基址找到自己的那份（`swapgs`），用完立刻换回去。这是入口的汇编代码里唯一一处碰内存里的状态的地方，所以它必须是每个 CPU 自己的。

## 其余的 CPU 是怎么启动的

启动 CPU 把内存管理、调度器都准备好（内核测试也跑完）之后，在加载 init 之前调用 `kernel::Smp::start_secondaries()`。它对每一个别的 CPU 做同样的事，一次一个：

1. 给它建好 idle 任务（`Scheduler::prepare_idle`）。它启动时就用这个任务的内核栈。
2. 把它要用的页表、栈、入口写进一块参数区，请硬件把它放到一段启动代码上。
3. 启动代码把页表装上、打开分页、换到高半区的栈，进入 `kernel::Smp::secondary_main()`。
4. 它在那里拿内核锁，设置自己的硬件（`hal::Cpu::init_secondary`：中断控制器、时钟），报告“上线了”，然后放掉锁，成为自己的 idle 任务（`Scheduler::run_idle`）：从此和启动 CPU 一样，没事就等中断，有任务就去运行。
5. 启动 CPU 等它报告之后再启动下一个：参数区只有一份。等的时候它得先把内核锁放掉，不然新 CPU 拿不到锁，报告不了。

第 2、3 步各架构不一样。

### arm64

设备树的 `/cpus` 下面每个 CPU 有一个节点，`/psci` 节点说明固件接口怎么调用（`hvc` 还是 `smc` 指令）；没有这些就不启动别的 CPU。启动一个 CPU 是一次固件调用：PSCI 的 `CPU_ON`，带上那个 CPU 的编号和入口地址 `secondary_entry`（`src/arch/arm64/boot/start.S`）。新 CPU 和启动 CPU 刚上电时一样：在物理地址上运行，MMU 和中断都关着。每个 CPU 有自己的 GIC CPU 接口和自己的通用定时器，`init_secondary` 把它们打开。

### x86（i686 和 x86_64）

x86 没有固件可以代劳，要自己用 **Local APIC**（每个 CPU 自己的中断控制器，`src/drivers/x86/lapic.cpp`）给别的 CPU 发两种“处理器间中断”：先 `INIT` 让它复位，再 `SIPI` 告诉它从哪一页开始执行。

被叫醒的 CPU 和一台刚开机的 8086 一样：16 位实模式，只能从 1MB 以下的地址开始。所以启动代码（`src/arch/<arch>/boot/ap_trampoline.asm`）不能在内核映像里原地运行：启动 CPU 把它整段拷到物理地址 0x8000（PMM 从不把内核映像之前的页帧分出去，那一页没有主人），再发 `SIPI`。它一路走到内核所在的模式：

- i686：实模式 → 保护模式 → 打开分页；
- x86_64：实模式 → 保护模式 → 打开分页进长模式 → 64 位。

打开分页的那一刻它还在物理地址上运行，而内核自己的页表里低地址早就没有映射了，所以启动 CPU 专门准备一张“启动用的页表”：内核的那张，加上低地址的恒等映射。进了 C++ 代码（`i686_ap_entry` / `x86_64_ap_entry`）之后，新 CPU 装上自己的 GDT 和 TSS、大家共用的 IDT，换回内核的页表。

别的几件事：

- **有几个 CPU。** 固件在内存里留了一组 ACPI 表描述这台机器，其中 MADT 列出每个 CPU 的 Local APIC（`src/drivers/x86/acpi.cpp`：从低端内存里的 RSDP 找到 RSDT，再找到签名是 `APIC` 的那张表）。表上只有一个 CPU 时什么都不做，中断的设置原样不动。读不到表时退回去按顺序试 APIC ID，试到 200 毫秒没人应为止。
- **时钟。** PIT 的中断经 8259 只送到启动 CPU。别的 CPU 用自己 Local APIC 里的定时器（100Hz，频率在启动时对着 PIT 量出来）。“开机以来多久”仍然是启动 CPU 数 PIT 的滴答，所有 CPU 读同一个数。
- **设备中断**照旧走 8259，只到启动 CPU：它的 Local APIC 把 LINT0 设成直通外部中断，别的 CPU 把 LINT0 屏蔽掉。没有用 I/O APIC。
- **Local APIC 的寄存器**是物理地址 0xFEE00000 的一页，要映射进内核：x86_64 上在直接映射区里给它所在的 2MB 补一项，i686 上映射到内核地址空间的倒数第二页。

## CPU 之间打招呼

有两件事一个 CPU 要让别的 CPU 知道，办法是给它们发一个中断（`hal::Cpu::kick_others()`）。中断不带内容，到了就算数：

- **有任务可以运行了。** 一个 CPU 把任务放进就绪队列时，如果有别的 CPU 正闲着等中断，就叫醒它们（`sched.cpp` 的 `enqueue_locked`）。不叫的话，那个任务要等到某个闲着的 CPU 自己的下一次时钟中断（最多 10 毫秒）才被发现。这里不会漏：idle 任务是在调度锁里看队列、标记“我要停了”，放了锁再停下的，而叫的一方是拿着同一把锁看标记的；它要么还没标记（那它接下来检查队列时会看到这个任务），要么已经标记了（那中断会把它从等待里叫出来，哪怕它还没来得及停下——停下和开中断是一个原子动作）。
- **`kill` 一个正在别的 CPU 上运行的进程。** 终止请求只是记在目标身上，要它自己进了内核、走到返回用户态的出口才生效。埋头在用户态计算的进程自己不会进来，所以发个中断让它进来一趟。

arm64 上这是 GIC 的 0 号软件中断（SGI），目标写“除自己以外的所有 CPU”；x86 上是 Local APIC 的一个处理器间中断（65 号向量），同样发给除自己以外的所有 CPU。处理函数什么都不做：闲着的 CPU 已经醒了，在用户态的 CPU 已经经过了抢占点。

## 用户态能看到什么

`cpu_info(&count)`（31 号系统调用）返回调用者此刻在哪个 CPU 上，`count` 得到正在运行的 CPU 个数。自检用它确认两件事：用户进程确实在不止一个 CPU 上运行过；每个 CPU 一个进程各自埋头算 300 毫秒，全部算完用的时间远少于一个接一个算的时间。自检还量了“被叫醒要多久”：一个进程让另一个变成就绪之后自己继续占着 CPU，看另一个要等多久才在别的 CPU 上运行起来（在 arm64 上有意义；x86 的时钟一格 10 毫秒，量不出来）。

## 当前的限制

- 还在那把大锁底下的：进程管理（`fork`、`exec`、`exit`、`waitpid`、`kill`）、`mem_grant`、硬件访问的调用、设备中断的入口。它们不频繁，或者（进程管理）要动的东西太多，暂时不值得拆。
- 调度锁是全局的一把：所有 CPU 的 IPC 和任务切换都要经过它。临界区很短（几十条指令，不含任何拷贝用户内存的动作），但 CPU 多了它会是下一个瓶颈；到那时的办法是每个 CPU 一个就绪队列。
- IPC 找“谁在向我发消息”是扫一遍任务表（64 项），在调度锁里。
- VMM 的锁是全局的一把，而且拿着它的时候关着中断：两个进程同时改各自的页表也要排队，复制、销毁整个地址空间（`fork`、进程退出）期间别的 CPU 改不了页表。
- 没有 CPU 亲和性，也不做负载均衡：谁空了谁取队首。
- x86 上时间由启动 CPU 的 PIT 中断推进：它关着中断等内核锁的时候，滴答可能丢。
- i686 上 Local APIC 的寄存器映射在内核地址空间的最末尾；内存有 2GB 时那里被直接映射区占着，这时不启动别的 CPU。
- 内核测试只在启动 CPU 上跑，在其余的 CPU 启动之前。
