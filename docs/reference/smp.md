# 多个 CPU

CastorOS 可以用机器上所有的 CPU 同时运行用户进程。**目前只有 arm64 会把其余的 CPU 启动起来**；i686 和 x86_64 上同样的代码在一个 CPU 上运行（HAL 里“启动其余 CPU”那个函数直接返回 0）。

```bash
make run ARCH=arm64 SMP=4       # 给虚拟机 4 个 CPU
make test ARCH=arm64 SMP=4      # 带着 4 个 CPU 跑全部测试
```

不写 `SMP` 就是一个 CPU。QEMU virt 上用的是 GICv2，最多 8 个。

## 办法：一把内核锁

内核原本的假设是只有一个 CPU：关了中断就没有别人（见 [同步](../concepts/06-synchronization.md)）。有了几个 CPU，这个假设靠一把锁留住：

> 任何 CPU 执行内核代码之前都要拿到内核锁，所以同一时刻只有一个 CPU 在内核里。

内核里的数据结构（就绪队列、任务表、物理页位图、堆、IPC 的状态……）因此一个都不用改，原来“关中断”保护的东西现在照样安全。用户态的代码不归这把锁管：几个 CPU 可以同时运行几个用户进程，这就是多 CPU 带来的全部好处。微内核在这一点上占便宜——文件系统、网络、驱动都是用户进程，它们真的在并行；内核自己每次进来只做很短的事，排一下队代价不大。

代价也很清楚：**内核本身不并行**。两个进程同时做系统调用，要一个等另一个。

锁在 `src/kernel/smp.cpp`（`kernel::KernelLock`），什么时候拿、什么时候放：

| 时候 | 做什么 |
|------|--------|
| 从用户态进内核（系统调用、中断、异常） | `enter()`：拿锁，拿不到就空转着等 |
| 回用户态之前 | `release()`：放锁 |
| 中断打断的是内核自己（这个 CPU 已经拿着锁） | `enter()` 只把嵌套计数加一，回去时 `leave()` 减一 |
| idle 任务没事可做，停下来等中断之前 | `release()`；醒来之后 `enter()` |
| idle 等中断的那段时间里来了中断 | 处理函数自己 `enter()`、自己 `leave()` |

**锁是 CPU 拿着的，不是任务拿着的。** 任务切换时锁不换手：CPU 拿着锁从任务 A 切到任务 B，B 接着往下走，回用户态时把锁放掉。这一点让调度器不用改：`schedule()` 里“把换下去的任务放回就绪队列”发生在真正切换之前，如果这时别的 CPU 能进调度器，它可能把这个任务取走、在它还没让出来的栈上运行。有内核锁在，别的 CPU 要等这边切换完、回了用户态（或者进了 idle 的等待）才进得来。

一个新进程第一次运行时不经过“从异常返回”的那条路，而是由任务切换的代码直接跳进用户态；所以那里也要放一次锁（arm64 的 `context_asm.S` 在 `eret` 之前调用 `kernel_lock_release`）。

`release()` 是“不管嵌套了几层都放掉”，而不是减一：有的路径进来了就不再按原路回去（进程在异常处理里退出，换上来的是另一个任务），而回用户态时这个 CPU 一定不该再拿着锁。

## 每个 CPU 自己的东西

每个 CPU 有一个编号，`hal::Cpu::id()`，0 是启动时的那个（arm64 上放在 `TPIDR_EL1` 寄存器里）。下面这些每个 CPU 各有一份，按编号放在数组里：

| 什么 | 在哪里 |
|------|--------|
| 正在运行的任务、idle 任务、时间片计数、“该换人了”的标记 | `src/kernel/sched.cpp` 的 `per_cpu[]` |
| 中断嵌套了几层 | `src/kernel/interrupt.cpp` |
| 现在用的是哪张页表 | `src/mm/vmm.cpp` |
| 内核锁拿了几层 | `src/kernel/smp.cpp` |

就绪队列只有一个，所有 CPU 共用：哪个 CPU 进了调度器，就从队首取下一个任务。所以一个进程这次在 CPU 0 上运行，下次可能在 CPU 2 上——它的寄存器、浮点状态、页表都跟着 PCB 走，哪个 CPU 都能接着运行它。每个 CPU 有自己的时钟中断，各自给自己正在运行的任务计时间片。

设备中断只送到 CPU 0。任务表最前面的 8 个 PCB 留给各个 CPU 的 idle 任务。

## 其余的 CPU 是怎么启动的（arm64）

启动 CPU 把内存管理、调度器都准备好（内核测试也跑完）之后，在加载 init 之前调用 `kernel::Smp::start_secondaries()`：

1. 设备树的 `/cpus` 下面每个 CPU 有一个节点，`/psci` 节点说明固件接口怎么调用（`hvc` 还是 `smc` 指令）。没有这些就不启动别的 CPU。
2. 对每一个别的 CPU：给它建好 idle 任务（它启动时就用这个任务的内核栈），把它要用的页表寄存器的值、栈、编号写进 `secondary_boot`，然后用 PSCI 的 `CPU_ON` 请固件把它放到 `secondary_entry`（`src/arch/arm64/boot/start.S`）。
3. 新 CPU 和启动 CPU 刚上电时一样：在物理地址上运行，MMU 和中断都关着。`secondary_entry` 把页表装上、打开 MMU、换到高半区的栈，进入 `kernel::Smp::secondary_main()`。
4. 它在那里拿内核锁，设置自己的中断控制器接口和时钟（`hal::Cpu::init_secondary`），报告“上线了”，然后成为自己的 idle 任务（`Scheduler::run_idle`）：从此和启动 CPU 一样，没事就等中断，有任务就去运行。
5. 启动 CPU 等它报告之后再启动下一个：`secondary_boot` 只有一份。等的时候它得先把内核锁放掉，不然新 CPU 拿不到锁，报告不了。

## 用户态能看到什么

`cpu_info(&count)`（31 号系统调用）返回调用者此刻在哪个 CPU 上，`count` 得到正在运行的 CPU 个数。自检用它确认两件事：用户进程确实在不止一个 CPU 上运行过；每个 CPU 一个进程各自埋头算 300 毫秒，全部算完用的时间远少于一个接一个算的时间。

## 当前的限制

- 只有 arm64。x86 要另外做：用 LAPIC 的时钟和 INIT/SIPI 启动其余的 CPU，每个 CPU 自己的 GDT、TSS 和系统调用入口的内核栈。通用的部分（内核锁、每个 CPU 的状态）已经在所有架构上运行，只是 x86 上永远只有 0 号 CPU。
- 内核不并行（见上）。要并行就得把这把大锁拆成各个数据结构自己的锁。
- CPU 之间不互相发中断。一个 CPU 把任务放进就绪队列时，别的 CPU 如果正停着等中断，要到它自己的下一次时钟中断（最多 10 毫秒）才发现；`kill` 一个正在别的 CPU 上运行的进程，也是到它下一次进内核时才生效。
- arm64 上每次换地址空间都把所有 CPU 的 TLB 清空（没有用 ASID），多 CPU 时这比单 CPU 更浪费。
- 没有 CPU 亲和性，也不做负载均衡：谁空了谁取队首。
- 内核测试只在启动 CPU 上跑，在其余的 CPU 启动之前。
